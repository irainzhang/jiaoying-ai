# 叫应 AI · 防汛转移协同

<img src="dist/assets/logo-lockup.png" alt="叫应 AI — 防汛转移协同" width="480">

面向比赛评委和团队讨论的独立本地原型。沿用“叫应”的预警、受威胁家庭、包保责任与转移反馈场景，重点演示需求核实、路径规划、跨户车辆分配及安置容量约束。

**全部人员、角色、路网、耗时和资源均为虚构。没有接入原“叫应”系统，没有调用大模型，没有真实消息、定位或调度指令。** 本版实际运行路径与组合搜索算法；回执整理与未接模型时的对话为有限文本规则。已新增 AI 协同助手交流页，并按 DeepSeek 预留可选后端，等待后续账号配置。

## 打开与运行

双击 `启动演示.cmd`，或用浏览器打开 `dist/index.html`。无需安装、联网、地图密钥和模型密钥。刷新或点击重置会恢复初始演练，未导出的记录不会保留。

也可在本目录运行 `node server.mjs`，访问 `http://127.0.0.1:8765/#assistant`。使用支持内置 fetch 的 Node.js 22 或更新版本；服务器只监听本机回环地址，端口可用 `JIAOYING_PORT` 环境变量更改。

GitHub Pages 静态版提供完整演练和本地规则对话，不运行模型网关。静态页面不会请求不存在的模型接口；DeepSeek 需要下载项目后在本机配置。

## 六个模块

| 模块 | 主要操作 | 与其他模块的关系 |
| --- | --- | --- |
| AI 协同助手 | 提问、查看当前情况与路线解释、提出封桥重算、带入现场反馈 | 回答携带输入版本；点击操作卡才执行，旧卡失效；当前是本地导览 |
| 预警叫应 | 模拟发布任务，逐户记录包保员接收、已联系家庭 | 接收、联系和转移进度分别统计 |
| 人员与资源 | 编辑人数、优先级、协助、轮椅、接人时间；编辑车与安置容量和可用状态 | 保存有效修改才更新输入版本，取消编辑不影响方案 |
| AI 路径与调度 | 生成两种方案、选择单车路线、查看逐站时间；注入封桥或资源停用 | 同一快照计算简单基线和联合调度，旧方案不能跨版本确认 |
| 转移反馈 | 核对回执字段；模拟上车、到达上报、人工核验 | 普通回执不触发重算，新增核实需求影响出发前规划 |
| 方案依据 | 定位、实际能力、六个评审问题、来源与后续材料 | 辅助讲解，不是值守流程的必经步骤 |

所有页面共享同一场演练，始终对本次全部家庭求解。只展示某辆车不会改变求解范围。

## 建议演示顺序（5—7 分钟）

可先打开侧栏第一项“AI 协同助手”，问“生成接送方案”，点击计算卡；再问“如果东桥封闭会怎样”，核对建议后点击重算。业务页右下角也能随时进入交流。DeepSeek 后续接入步骤见 [AI接入说明.md](AI接入说明.md)。

1. **预警到户：**在预警叫应页模拟发布任务。演示一户“包保员收到 → 登记已联系”，指出两者都不代表已转移。
2. **需求核实：**在人员与资源页编辑南湾户，勾选“需要上门协助”。保存后观察优先级和接人时间联动；也可展示取消编辑不生效。
3. **接送安排：**进入 AI 路径与调度，生成草案。点击 1 号车，查看每一户的接送顺序、经过的道路、到户时间及安置终点。
4. **出发前道路变化：**先确认草案，再打开“东桥封闭”。旧方案失效，确认按钮不再出现；重新计算后观察北桥路线。
5. **资源不足：**停用 2 号车，重新计算。查看未安排家庭和同条件基线。若确认可行部分，需要明确勾选知晓未安排家庭，并填写协调措施；未安排者继续保留。
6. **执行闭环：**在预警页完成所有已安排家庭的接收和联系记录，进入转移反馈，开始模拟执行。按某辆车的接人顺序登记上车；该车接完后才可上报到达，再人工核验。
7. **异常反馈：**对尚未上车且由普通车辆接送的家庭，登记新增轮椅需求。执行中的路线不自动更改，该户推进按钮暂停，进入待人工协调清单。
8. **回答评审：**打开方案依据，解释实际算法、未接模型和数据性质。可导出演练 JSON 保存输入、两套方案、原始回执、人工修正及操作记录。

只想演示路线时，可以直接进入调度计算；正式开始模拟执行才要求完成演练任务发布和已安排家庭的联系记录。

## 计算规则与公平比较

- 道路图为 16 个节点、22 条无向边。Dijkstra 只使用设定为开放的边，不用直线补齐不可达路线。
- 每户不拆分，人数包含同行者；每车从集结点单趟出发，沿途接人，最后到一个安置点。
- 每辆适配车有 1 个轮椅位，已计入车辆总名额。两户各需轮椅位时不能共用同一个位置。
- 同时检查车辆总容量、轮椅位、安置点累计接收人数、路段连续性、封路、接送顺序、时间与人数守恒。
- 候选排序依次比较：优先转移户覆盖数、需协助户覆盖数、总覆盖人数、重点人员加权到户等待、最后抵达时间、所有车辆行驶总时间、全体人员加权等待。
- 每辆车、家庭子集、安置点先保留一条局部候选，再搜索候选组合。称“约束下的候选组合搜索”，不声称证明全局最优。本版最多 8 户，未验证全区规模。
- 重点人员平均等待 = 已安排且优先级大于 1 的各户到户时间 × 人数之和 / 对应人数。到户时间包含此前道路和接人用时。最后抵达是所有已安排车辆抵达时间的最大值。
- 协助优先级与需求同步：选择“需协助”意味着需要上门协助；协助需求至少为优先级 2，至少 5 分钟接人，轮椅至少 6 分钟。这些都是需要业务方核实的演练规则。
- 简单基线按优先级、家庭编号排序，将下一户追加给可最早到户的可行车辆；车辆第一次选定安置点后不改变。基线遵守同样硬约束，不代表真实人工派车。
- 两种方法始终使用同一输入快照。接送对象不同时，页面先提示覆盖差异，不把时间差解释为同批人员效率提升。即使对象相同，重点等待与最后抵达也可能存在权衡。

## 状态与边界

保存计算条件或注入事件会更新输入版本，撤销旧确认。两套旧结果不再作为当前方案显示。导出记录保留原计算快照，不能把新人数套用到旧方案。

部分方案可以人工确认可行部分，但必须登记余留家庭的协调说明。零覆盖方案不能确认。只有当前已确认方案、模拟任务已发布且已安排家庭均有联系记录，才能开始模拟执行。

进入执行后冻结人员、资源、道路和方案；不支持车辆途中重排。执行表独立维护待接送、已登记上车、到达待核验、已人工核验。未接完本车家庭不能登记安置点到达；文字“收到”“已通知”“已到达”都不会改变执行表。

回执保留原文和规则建议；演示者可以修改建议复选框，跨页保留人工修正。普通反馈不使方案失效。新增已核实的协助或轮椅需求，在出发前更新台账，在执行中列为待协调并暂停该户继续登记；本版没有解除协调事项、途中换车或改道流程，需要重置后组织下一轮演练。

反馈页汇总为“本次转移对象”，不是宣称全部人仍待转移。上车、到达待核验和已核验分别统计，不能把部分人员核验当作全员完成。

## 评审材料与下一步

优先需要：实际典型流程、原程序可公开功能资料、业务约束、一个可公開演示区域的路网与安置点来源。随后配置已选定的 DeepSeek 接口并准备公开测试语料，再实现语义提取、公开预案检索、模型工具调用与依据追溯。

只有公开报道，尚未获得原程序代码、接口或合作授权。原产品已有导航等能力，不能称作本队首创。原产品事实来源：[北京广播电视台报道](https://item.btime.com/43qb8qcv8098jsqi1od0gmoih04)。本队新增实现及限制见本页的计算规则、状态边界与验证记录。

赛事手册要求数据集和外部知识库公开可获取。内部授权、脱敏不自动等于公开；合成数据参赛口径仍待组委会核实。当前公开可复现程度、数据资格和真实成效不能混为一谈。

本版 44 项自动测试通过，新增对话意图、上下文失效、回执转入、执行冻结、网关配置与错误、并发控制，以及迟到响应不能覆盖手动本地模式或重置后的演练。原算法与状态检查包括独立最短路校对、16 种事件组合下基线约束、编辑原子性、版本失效、部分确认、执行冻结、接人顺序、回执不确认安全和新增需求拦截。

原 V2 浏览器已检查五个业务页、取消与保存编辑、单车路线、封路重算、部分方案拒绝与确认、跨页人工修正保留、联系门槛、上车到达核验链及执行中新增需求拦截。检查了 390 像素视口；路网和宽表在各自区域滚动。

可选 WebMCP 使用同一状态源：读取状态、生成两种草案、设置四种演练事件；输入严格检查，执行阶段拒绝修改。可选模型网关仅在本机运行；尚未配置或调用 DeepSeek，没有实际通知。
