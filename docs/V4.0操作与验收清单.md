# V4.0 操作与验收清单

2026-10-05。供团队验收和第一次使用的人照着操作。主线是：**空白开场 → 一页核对需求 → 发布 → 各车执行 → 结束留档**。新版本保留旧记录，不会为了显示空白而清空已有任务。

## 五个模块各做什么

| 模块 | 只需要完成的事 | 常用步骤 |
|---|---|---|
| 指挥台：需求录入 | 把新增需求变成可核对的本场人员需求 | 上传或说出一批 → 核对表直接改 → 保存；有缺项集中补齐 |
| 指挥台：任务执行 | 看安排、发布、跟踪车辆、结束本场 | 看覆盖与缺口 → 发布 → 跟踪各车回执、核验到达 → 结束 |
| 指挥台：任务记录 | 保存结果、交接未完成事项、开始下一场 | 看本场摘要 → 导出 → 新建；需要时查看或清理历史 |
| 现场端：执行任务 | 完成本车当前一步 | 选车辆 → 接令、登记联系 → 发车、上车、到达 |
| 现场端：补报情况 | 把新发现的人或异常一次报清 | 说一批或输入一批 → 核对 → 确认提交 |

资源配置、模拟天气、详细路线、算法比较、来源说明、情景示例和 API 说明都是辅助入口，不必全部使用才能完成一场任务。

## 1. 从真正的空白开始

1. 如果顶部已有未结束任务，先看本场人数和进度；不再继续时，点击“结束当前任务”，选择提前结束。已上车、到达及未核实事项照原样保留。
2. 新建时选**空白任务**，使用瑞安真实道路。新场人员为 **0 人**；地图与资源可保留，人员不会自动出现。
3. 只在讲解功能时主动选择**示例演练**。它包含合成的 15 人，不是上传名单，也不是瑞安实际人口。
4. 如要使用自己掌握的车辆、接收容量，在发布前配置资源；车辆起点和接收点必须对应当前地图节点。修改后查看本场草案。

验收：未选示例时，空白新场显示 0；上传 20 后显示 20，不会变成 35。旧浏览器原有 15 人任务仍保留，需要由人选择结束，更新网页不会偷偷改它。

## 2. 上传与一页核对

1. 在需求录入上传 `.xlsx` / `.csv`，或通过语音、文字说出新增需求。整批最多 100 条；明确“新增”，避免把当前总量重复增加。
2. 在核对表直接改**人数、村庄、接人点、协助人数、轮椅人数和同行关系**。修改会保留原始值；总人数与子集人数不一致会阻止提交。
3. 先看人数算式：**本场已有＋此次新增＝保存后人数**。现场待核实补报单列，不提前加进有效总数。
4. 看“信息齐全 / 待补”汇总。已登记村庄与集合点可以按名称或编号匹配；同名有歧义时用编号。修改村庄会清除原接人点，防止名称换了、地图仍挂在旧村。
5. 有 WGS84 坐标的需求由有限道路网匹配；超出范围、距离可用节点太远、普通地点名未匹配的需求保留待定位。名称相似不会变成自动地理编码。
6. 未确认的协助、轮椅或同行关系保持空白。只有明确核对一批人确实没有特殊需求时，才用批量补齐；它不会自动取消已填的轮椅需求。
7. 信息完整时保存并查看安排；信息不完整时保存需求并补齐信息。**保存不是发布；信息齐全也不代表资源一定足够。**

验收：把预览中的 6 改为 8，算式同步改变，原值仍可查看；把村庄改为另一村，原接人位置不会继续使用。错误子集（例如 2 人中轮椅 3 人）不提交。未知数量不自动写成 0。

## 3. 发布与逐车执行

1. 指挥台进入任务执行，核对安排人数、未安排人数、目的地与原因。点击发布，无需手输确认文字。
2. 现场端选择负责车辆，接收当前版本任务。已经联系到的本车人员可以勾选后批量登记；未联系人员不能冒充已联系。
3. **本车就绪即可发车**，不等其他车辆全部联系完。其余车辆继续自己的接令和联系步骤。
4. 按现场事实登记上车、到达；指挥台的地图和状态随回执更新。到达不自动等于人工核验，核验后才计入完成。
5. 路况、资源或人员变化后，查看新草案并人工重新发布；旧方案不能继续冒用新条件。
6. 已送达的空车还要接下一批时，准备下一趟，核对新路线、重新发布，再接令和发车。车辆从上次送达位置继续，原送达记录与接收占用保留。

验收：只让一辆车接令、联系和发车，其他车仍可未联系；未发车的另一辆车不能登记上车。完成第一趟后接收人数不归零；第二趟不自动发布、不自动把人员登记到达。

边界：当前是逐趟重新计算，不是一次性全局多趟优化。原接送组不会为了挤入剩余座位或接收容量而自动重新拆分；缺口仍可能存在。车辆动画是演示，地图回执位置不是 GPS。

## 4. 一句话补报新增人员

1. 在现场端补报情况说“这里又发现 3 人，其中 1 人需要协助，无轮椅，可分组”。沿用本车当前接人点，或先选择一次村庄和集合点。
2. 核对整批数量和位置后一次确认，无需逐人点击。
3. 指挥台收到待核实补报。核实采纳前，有效总人数保持原数；采纳后才增加 3 人并形成新草案。
4. 若原话只说“又发现 3 人”，协助、轮椅和同行关系仍待补，不替现场人员猜测。

验收主线：空白 0 → 上传 20 → 补报 3 待核实时仍是有效 20、待核实 3 → 采纳后有效 23。默认资源首轮实际只能安排一部分，不能要求系统假报 23 人全部解决。固定样例的实际结果见 [可复现评估](V4.0可复现评估.md)。

## 5. 结束、归档与交接

1. 点击“结束当前任务”，看已核验、待接、车上、到达待核验和未决事项摘要。
2. 所有有效人员已核验、且无未决事项，才能按完成结束；否则只能提前结束，不能把未完成者改成已完成。
3. 结束后两端只读。新建、重置、切换情景及导入另一场记录都会先保留原场快照。
4. 新建空白任务时，可以明确选择结转**尚未上车的待接需求**；结转有来源记录，新安排需重新发布。车上、已到达人员不会自动移入下一场；旧场待核实或协调事项继续保留在旧记录中，需人工交接。
5. 历史达到 10 场或 4 MB 时，先导出并确认备份可用，再选择需要清理的历史。系统不自动删除最早一场，也不允许删除当前场。
6. 同一任务的旧备份不能覆盖当前事实；如只想比对，在另一浏览器查看备份。导入另一场会保留被替换的当前场。

验收：提前结束后记录里的车上人数保持原数；新场为空或只包含人明确结转的未上车需求。没有备份确认不能清理历史；当前任务不可清理。

## 6. 两端怎样同步

| 方式 | 操作 | 数据边界 |
|---|---|---|
| GitHub 页面 | 同一浏览器开指挥、现场两个标签页 | 同浏览器保存并联动；别人手机访问同一 GitHub 地址看不到你的任务 |
| 本机服务 | `node server.mjs`，默认 8769 | 仅本机回环，不向同网手机开放 |
| 局域网房间 | `node lan-server.mjs`，默认 8770；两端打开终端打印的加入链接 | 同一 Wi-Fi、同一房间共享；独立房间存档，和 GitHub 记录隔离 |

局域网不会自动开公网或改防火墙。每次启动默认独立房间；关闭、继续旧房间以及换端口见 [LAN_README](../LAN_README.md)。手机 HTTP 页面可能不支持浏览器语音按钮，可用手机键盘听写输入文字。浏览器语音可能联网，应用不保存录音。

## 7. 守护助手、天气和 API

守护助手的本场入口读取主台当前人数、路线、缺项，使用本地的状态读取、草案计算和报告准备工具；发布仍返回主台由人点击。次级独立沙盘的 21 工具使用另一套演练底数，不能混同本场人数。两处均未连接真实大模型。

雨量继续模拟，展示统计时段、来源和更新时间；同级变化不反复重排，达到演练阈值才复核。彩云接口与后续自动事件预留，不预测水深，不把模拟演练等级当正式天气预警。

API 接入位置是 `dist/guardian/agent/api-config.js`，守护面板顶部“自己接入 API”可查看说明。推荐后续完成后端代理，真实密钥放 `.env`；公开网页不填密钥。本版本未部署该转发端点。

## 验收如何记录

程序回归、脚本计算、浏览器操作和真人上手四类证据分开记录。评估 JSON 只证明固定输入下的计算与状态守恒，不证明现场效率、模型准确率或灾害损失下降。

建议邀请 3—5 位未看过系统的人，每人独立做“上传→发布→补报→结束”。记录是否成功、完成秒数、求助次数、误操作、最卡的一步和原话反馈。不填猜测数值，不采集真实居民资料；本轮没有伪造这份真人记录。
