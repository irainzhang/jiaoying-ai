# 动作按钮与执行闭环

## 适用场景

- 研判与方案已完成，需要进入上报、派单、发布、状态回填的流程。
- 现场反馈新增险情、路段阻断、口播雨量变化，需要评估是否重新研判。
- 用户说「派下去」「发布方案」「通知街道」「更新一下执行情况」。

## 核心规则

1. **每一条助手回复都必须附带动作按钮。** 动作按钮是执行闭环的唯一入口，
   不是装饰；即使回复只是解释性的，也要给出可选的下一步按钮。
2. **改变状态必须通过调用工具完成**，只靠对话描述不算推进工作流。
   状态变化要能在轨迹中留痕，并同步到监控与方案视图。
3. **`publish_dispatch_plan` 需要人工确认**，智能体绝不自行批准。
4. **未达阈值的输入变化只累积并提示，不静默重算方案。**
5. 发布结果通过**现有政务通讯工具**送达，本系统不设独立接收端，
   因此智能体要产出可直接粘贴的通知文本。

## 动态触发标准（防止方案频繁变动）

评估输入变化是否需要重算方案时使用以下阈值：

| 变化项 | 阈值 |
| --- | --- |
| 累计雨量增量 | 20 mm |
| 险情严重等级 | ≥ 3 级 |
| 新增险情条数 | 2 条 |
| 新增阻断路段 | 1 条 |
| 受影响人数增量 | 3 人 |
| 方案静默时长 | 30 分钟 |
| 最短重算间隔（冷却期） | 15 分钟 |

处理逻辑：

- 任何输入变化一律被记录并累积。
- 命中任一阈值且不在冷却期内，才**建议**重新研判；重算仍需一次按钮确认。
- 命中阈值但仍在 15 分钟冷却期内，只提示「已记录、暂不重算」。
- 未命中阈值时，只累积并提示，**不得静默重算**。
- 方案生成超过 30 分钟，即使没有新变化，也提示复核一次。

## 执行步骤

1. 判断当前处于闭环的哪一步，缺哪一步就补哪一步，不要跳步。
2. 现场新增险情：调用 `submit_hazard_report` 记录位置、类型、严重等级与描述。
3. 评估是否重算：调用 `evaluate_trigger` 读取命中项、未达阈值项与冷却期状态；
   命中时把「是否重新研判」作为一个需要人工确认的动作按钮给出。
4. 方案确认后：调用 `create_dispatch_tasks` 把方案拆成可执行任务，
   写入任务清单并推动工作流。
5. 发布方案：调用 `publish_dispatch_plan`。该工具需要人工确认，
   智能体只能发起确认请求，不得自行批准；发布后生成可粘贴的通知文本。
6. 执行反馈：调用 `update_task_state` 更新任务状态（已接受/进行中/完成/受阻），
   受阻任务需注明原因并回到缺口清单。
7. 每次状态变更后，重新评估触发标准，判断是否需要提示复核方案。
8. 每一轮回复结束前附带下一步动作按钮，形成闭环而不是断点。

## 输出要求

- 每条回复都带动作按钮，按钮文案与工具动作保持一致，避免同一动作多种叫法。
- 通知文本必须可直接粘贴使用，包含：事由、时间、范围、对象、安排、注意事项、
  反馈方式，最后标注「演练模拟文本，正式发布需履行审批程序」。
- 明确区分「已记录」「已建议」「已执行」「需人工确认」四种状态。
- 重算建议必须说明命中了哪一条阈值、当前是否处于冷却期。
- 存在未解决缺口时，在通知文本与状态说明中一并保留，不得只报已完成部分。

## 禁止与边界

- **不得自行批准 `publish_dispatch_plan`**，也不得伪造人工确认。
- 不得用对话回复替代工具调用来声称「已经发布了」「已经派单了」。
- 不得在未达阈值时悄悄重算方案，也不得绕过冷却期连续重算。
- 不得把动作按钮做成没有对应工具、点了没有状态变化的装饰按钮。
- 不得声称本系统有独立接收端 App 或独立指挥平台；发布依赖现有政务通讯工具。
- 不得把演练模拟的通知文本当作真实公文口径，必须保留演练与审批提示。
- 不得声称消息已真实送达某个单位或个人，除非工具返回了对应状态。
